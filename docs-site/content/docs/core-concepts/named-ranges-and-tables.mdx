Named references let formulas describe intent instead of coordinates.

## Why they matter

- `Revenue_Q1` is easier to audit than `Sheet1!B2:B100`.
- Table-style references stay meaningful as data grows.
- Names can centralize workbook assumptions.

## Common usage patterns

- Use workbook-level names for constants and key ranges.
- Use table columns for row-wise calculations.
- Keep naming conventions consistent across teams and bindings.

## Short example

```text
Name: TaxRate = 0.0825
A2 formula: =A1 * TaxRate
```

## Scope rules
Named ranges can be workbook-scoped (visible everywhere) or sheet-scoped (visible only within that sheet). When both exist with the same name, sheet-scoped names take precedence within their sheet. The engine resolves names during reference binding, before evaluation.

## Structured table references
Structured table references (e.g., `Table1[Column]`, `Table1[@Column]`) are recognized by the parser. The `full-v0` SheetPort profile reserves native table selector support. Currently, layout-based selectors provide equivalent functionality for SheetPort manifests.

## Tables in saved XLSX files
[`formualizer recalc`](/docs/recalc-cli) recalculates Excel tables (ListObjects) in `.xlsx` files and leaves the table definitions untouched. It supports column and column-span references, `#Data`, `#All`, `#Headers`, `#Totals`, `[@Column]` / `[#This Row]` in the data body, and bare table names such as `SUM(Table1)`, which mean the data body. Calculated columns are recalculated from the formula stored in each row, so when you add rows with openpyxl, write the formula into every new row of the column before recalculating. Workbooks with table features outside the supported subset (for example connection-backed tables, computed `INDIRECT` text or defined names that refer to tables) are refused; see [Supported and refused](/docs/recalc-cli/supported-and-refused#excel-tables).

Loading an `.xlsx` file into a workbook (`load_workbook` in Python, `Workbook.fromXlsxBytes` in JavaScript, or `Workbook::from_reader` in Rust, with the default native reader or Umya) registers its tables with the engine under their display names. Structured references then resolve as for tables defined through the in-memory APIs, with the limitations below. The native reader skips a table part it cannot read rather than refusing the workbook; references to that table stay `#NAME?`.

## Known limitations of in-memory tables
Tables defined through the in-memory workbook APIs, or loaded from an `.xlsx` file as above, resolve structured references natively, without the XLSX recalc path above, and some forms are not yet handled correctly there:

- Calculated-column and totals formulas that refer to a whole column or section of their own table, such as `=SUBTOTAL(109,Table1[Qty])` in the totals row, can be reported as circular references. This-row references (`[@Qty]`, `Table1[@Qty]`, `Table1[[#This Row],[Qty]]`) read only their own row and are not.
- `INDEX` over a whole table or over `Table1[#Headers]` returns `#REF!`.
- Inserting or deleting sheet rows does not move or resize a table.

For these cases, use explicit A1 ranges in the in-memory APIs, or recalculate the saved file with `formualizer recalc`.
